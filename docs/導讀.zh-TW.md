# conclave 導讀（給第一次看這個專案的人）

這份文件用白話說明 conclave 在做什麼、為什麼這樣做，讓你可以在面試時把它講清楚。
數字（測了多少種子、抓到幾個 bug、效能多少）以 README 為準，這裡只講觀念。

## 一句話說明

conclave 是一個「三台以上的電腦一起保管同一份資料」的鍵值資料庫（像一本大家共用的字典：
key 是單字，value 是解釋）。就算其中一台當機、網路斷掉、硬碟寫到一半斷電，資料也不會錯、
不會丟，而且每個客戶端看到的結果都像只有一台機器在依序處理一樣（這叫「線性一致性」）。

讓它跟網路上幾百個學生寫的 Raft 作業不同的地方，不是功能多，而是**證據**：
我們寫了一個「模擬器」，用同一份程式碼在假的時間、假的網路、假的硬碟上跑幾萬次各種災難，
每一次都自動檢查結果有沒有違反線性一致性；再故意把程式改壞十種方式，證明模擬器真的抓得到。

## 要解決的問題

一台電腦存資料很簡單，但它壞了資料就沒了。所以要多台一起存。難的是：

- 網路會延遲、掉封包、重複、順序亂掉，甚至只斷單向。
- 機器會在任何時刻當機，硬碟上「還沒真正寫進去」的資料會消失，最後一筆甚至只寫一半。
- 客戶端送出請求後逾時，根本不知道到底成功了沒；如果重送，可能會被執行兩次。

在這些情況下還要保證：每一筆「回覆成功」的寫入永遠不會消失，而且大家讀到的順序一致。

## 七個關鍵觀念（附生活比喻）

### 1. Raft：選一個班長，大家照班長的筆記抄

所有寫入都交給「領導者」(leader)。領導者把每筆寫入記在自己的日誌，再請其他成員抄一份；
超過半數抄好了，這筆才算「定案」(committed)。領導者壞了，其他人投票選新的。
**比喻**：班會紀錄由班長寫，過半同學抄進自己的本子才算數；班長請假就重新選。
因為任兩個「過半數」一定有交集，新班長一定看得到所有已定案的紀錄。

實作在 `internal/raft/raft.go`，包含選舉前先「預投票」(pre-vote，避免一個斷線的同學回來亂發起選舉)、
快速倒退找出分歧點、快照、一次加減一位成員、把領導權交接給別人、ReadIndex 讀取。

### 2. 「先寫進硬碟，才可以答應別人」

投票和「我抄好了」這兩種話，都是承諾。承諾一定要在資料真的寫進硬碟（fsync）**之後**才能說出口，
否則當機重開後會忘記自己答應過什麼，可能投兩次票、或讓「已定案」的資料消失。
**比喻**：答應借錢之前先寫進記事本，不然睡一覺起來忘了，又答應借給別人。
這個順序集中在 `Flush()` 一個函式裡（`raft.go` 最後面），方便檢查也方便測試。
macOS 上一般的 fsync 不保證寫進硬碟的快取，所以我們用 `F_FULLFSYNC`（`internal/vfs/sync_darwin.go`）。

### 3. 預寫日誌 (WAL) 與「寫到一半」的偵測

每筆紀錄前面加上長度和 CRC32C 校驗碼（`internal/wal/wal.go`）。重開機時從頭讀，
讀到最後一段發現長度不夠或校驗碼不對，就知道是「斷電時寫到一半」，把它切掉（那段本來就還沒 fsync，
沒有答應過任何人，切掉是安全的）。如果是中間的檔案壞了，那不是斷電能解釋的，就拒絕啟動。
**比喻**：每頁筆記右下角寫頁碼加總，最後一頁字寫一半就撕掉重寫，中間某頁對不上就代表筆記本被動過。

### 4. 核心「不碰外面的世界」，所以可以被模擬

Raft 核心不看時鐘、不開執行緒、不直接讀寫檔案或網路。時間是外面一直呼叫 `Tick()`，
訊息是外面呼叫 `Step()`，硬碟和網路都是傳進來的介面。
**比喻**：演員只照劇本演，燈光、音效、天氣全部由導演控制。同一齣戲可以在真的舞台（正式模式）演，
也可以在攝影棚裡由導演製造暴風雨（模擬器）演，演員本人完全一樣。

### 5. 確定性模擬器：同一個種子，同一場災難

`internal/sim` 用一個種子 (seed) 決定所有隨機事件：哪個封包延遲多久、哪台機器何時當機、
硬碟最後一筆留下多少位元組、要不要分割網路……全部在單一執行緒、虛擬時間上依序發生。
所以失敗時只要印出種子，任何人都能一模一樣重現（`TestDeterminism` 檢查同一種子跑三次結果逐位元相同）。
模擬器還會特別挑「剛投完票」、「剛當上領導者」的瞬間讓機器當機，並模擬斷電時網路緩衝區裡還沒送出的封包一起消失，
因為 bug 通常就藏在這些轉折點。
**比喻**：飛行模擬器。真飛機不能故意讓引擎失火來練習，但模擬器可以，而且可以重播同一次失火。

### 6. 線性一致性檢查器：把大家的紀錄排成一條線

每個模擬客戶端記下「什麼時候送出、什麼時候收到、收到什麼」。檢查器（`internal/lincheck`）
嘗試找出一個先後順序，讓每個操作都像在它的時間區間內某一瞬間「瞬間完成」，而且結果符合一本普通字典。
找不到，就代表系統說謊了。逾時的寫入結果未知，可能做了也可能沒做，檢查器兩種都要考慮。
我們加了幾個有數學理由的剪枝，讓一段原本要搜尋 2.66 億步的紀錄變成 1.6 萬步。
**比喻**：警察拿到每個證人的「進門、出門時間和看到的東西」，要拼出一個不矛盾的事件經過；拼不出來就有人說謊。

### 7. 故意弄壞程式，證明測試抓得到（突變測試）

如果測試永遠都說「沒問題」，那可能是測試太弱。所以 `internal/mutation` 定義了十種「看起來很合理的錯誤寫法」，
例如：投票前沒檢查對方日誌夠不夠新、還沒 fsync 就先回覆、用舊任期的條目數票數就定案（Raft 論文的 Figure 8）、
重送的寫入被執行兩次……每一種都必須被模擬器在有限的種子內抓到。這些錯誤只有在測試程式裡才能開啟，正式的執行檔打不開。
**比喻**：消防演習時故意在某處點煙霧彈，確認偵煙器真的會響。

### 8. 客戶端 session：重送也只算一次

客戶端先註冊一個 session，每次寫入帶上 (session, 序號)。伺服器記住每個 session 最後執行到第幾號；
同一號再來就直接回上次的結果，不再執行。
**比喻**：網購付款時的訂單編號，按兩次「付款」也只扣一次錢。

## 檔案導覽

| 位置 | 做什麼 |
|---|---|
| `internal/raft/` | Raft 共識核心：`raft.go`（選舉、複寫、提交、快照、成員變更、交接、ReadIndex、Flush 的順序規則）、`log.go`（記憶體中的日誌）、`codec.go`（訊息編碼，網路和模擬器共用）、`types.go`（介面與型別） |
| `internal/wal/` | 預寫日誌：分段檔案、校驗碼、撕裂寫入修復、快照檔 |
| `internal/vfs/` | 檔案系統介面；正式版用真的檔案和 `F_FULLFSYNC` |
| `internal/simdisk/` | 假硬碟：記住哪些位元組真的寫進去了，當機時丟掉沒 fsync 的部分，還可能把最後一筆寫壞 |
| `internal/prng/` | 規格固定的亂數產生器，保證同一種子在任何 Go 版本結果相同 |
| `internal/kv/` | 字典本體：get/put/delete/cas，加上 session 去重 |
| `internal/node/` | 把 Raft、WAL、字典接起來，處理請求並決定回覆（正式版和模擬器共用這一層） |
| `internal/sim/` | 模擬器：事件佇列、假網路、故障注入、模擬客戶端、各種檢查、失敗報告 |
| `internal/lincheck/` | 線性一致性檢查器 |
| `internal/mutation/` | 十種故意的 bug（只能在測試中開啟） |
| `internal/transport/` | 正式版的 TCP 傳輸 |
| `internal/server/` | 正式版伺服器：主迴圈、HTTP API |
| `client/` | Go 客戶端函式庫（自動找領導者、重送、session） |
| `cmd/conclave/` | 執行檔：serve、get/put/delete/cas、status、members、transfer、bench、sim |
| `scripts/cluster.sh` | 在本機用隨機埠開三台組成叢集 |
| `test/e2e/` | 真的開三個行程、在負載下用 PID 殺掉再重開，最後用同一個檢查器驗證 |

建議閱讀順序：`internal/raft/types.go` → `raft.go` 的 `Flush` → `internal/node/node.go` → `internal/sim/sim.go` → `internal/lincheck/wgl.go`。

## 面試可能會問的 10 個問題

**1. 為什麼需要過半數，而不是全部？**
全部的話，任何一台壞掉就停擺。過半數可以容忍少於一半的機器故障，而且任兩個過半數集合必有交集，新領導者一定拿得到所有已定案的資料。

**2. 什麼是 Figure 8 問題？你怎麼處理？**
新領導者不能只因為「舊任期的條目已經在過半數機器上」就宣布它定案，因為之後另一個有更新任期日誌的機器可能當選並把它覆蓋掉。正確做法是只數自己任期的條目，舊條目跟著一起間接定案。我們有單元測試重現 Figure 8，也有對應的突變測試讓模擬器去抓。

**3. 讀取為什麼不能直接讀領導者的記憶體？**
領導者可能已經被網路隔離、別人選出新領導者並寫了新資料，它自己卻不知道。ReadIndex 會先用一輪心跳確認自己仍被過半數承認，才回答讀取。

**4. 「寫到一半」的資料怎麼處理？**
每筆紀錄有長度和 CRC32C；重開時最後一段讀不完整或校驗不過就切掉。那段沒 fsync 過，沒對任何人承諾，切掉不會遺失已確認的資料。

**5. 客戶端逾時重送，怎麼避免重複執行？**
session + 序號。同一號再來就回傳快取結果；更舊的號碼直接拒絕，避免很久以前的重送蓋掉新資料。

**6. 模擬器怎麼做到「同一種子結果完全一樣」？**
單一執行緒、虛擬時間、事件按（時間、插入順序）排序、所有隨機來自同一個種子的固定演算法、程式中不依賴 map 的走訪順序。測試會同時跑三次比對每個事件的雜湊。

**7. 怎麼知道模擬器真的有用，不是一直說 OK？**
突變測試：十種故意的 bug，每種都要在有限種子內被抓到；而且抓到的那個種子在沒有 bug 時必須通過，排除是模擬器自己的問題。

**8. 這個專案中模擬器真的找到過 bug 嗎？**
有。WAL 在「安裝快照檔」和「寫入作廢舊日誌的標記」之間當機時，第一次重開沒問題，但第二次重開會拒絕啟動，甚至默默丟掉已確認的資料。模擬器在測量另一個突變時發現，修好後加了回歸測試。另外模擬器的假客戶端本身也出過錯（把重複送達的舊拒絕訊息當成最新請求的結果），被檢查器抓到誤報，也一併修正。

**9. 線性一致性檢查不是指數時間嗎？怎麼跑得完？**
最壞情況是。我們按 key 分開檢查（線性一致性具有區域性），再加上有證明的剪枝：從來沒被任何人看到的逾時寫入可以當作沒發生、不改變狀態的套用可以略過、效果相同的逾時操作只試一個、被已失敗狀態涵蓋的狀態直接剪掉。另外和暴力列舉在隨機小歷史上比對結果完全一致。

**10. 效能如何？瓶頸在哪？**
在這台 Mac 上三台都跑在同一顆 SSD，每次 `F_FULLFSYNC` 約 3.7 毫秒，而且三個行程的 flush 會互相排隊，所以單一客戶端延遲約 10 毫秒；用很多客戶端時批次提交可以把吞吐拉高。改用一般 fsync（不保證斷電安全）延遲降到 1 毫秒以下。詳細數字和量測方法在 README。
